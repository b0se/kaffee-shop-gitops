DeklarativMan beschreibt was sein soll („3 Replicas, Image 1.27“), nicht wie man dorthin kommt. Kubernetes-Manifeste sind deklarativ; ein Shell-Skript mit 20 kubectl-Befehlen ist es nicht.Nur deklarative Beschreibungen lassen sich automatisch mit der Realität vergleichen. Das ist die Vorbedingung für alles, was Argo CD tut.
Single Source of TruthGenau eine verbindliche Quelle für den Sollzustand – bei GitOps: das Git-Repository.Die Antwort auf „welcher Stand ist der richtige?“ lautet ab jetzt immer: der Commit auf main.
DriftAbweichung zwischen Sollzustand (Git) und Istzustand (Cluster) – egal ob durch manuelle Änderung, Crash oder Controller.Mareikes scale --replicas=0 ist Drift. Argo CD macht Drift sichtbar (Modul 4) und kann ihn automatisch rückgängig machen (Modul 5, Self-Heal).
ReconciliationDer Regelkreis: Sollzustand lesen → Istzustand beobachten → Differenz berechnen → Differenz beseitigen → von vorn. Kubernetes-Controller arbeiten genau so; Argo CD hebt das Prinzip auf die Ebene „Git ↔ Cluster“.Argo CDs Application Controller läuft diesen Kreis standardmäßig alle 3 Minuten (plus bei Webhook-Events) für jede Application.

Was GitOps konkret bringt

Audit & Nachvollziehbarkeit

Jede Änderung ist ein Commit mit Autor, Zeitpunkt, Review. „Wer hat prod geändert?“ beantwortet git log.

Rollback = git revert

Kein Spezialwissen nötig. Der alte Zustand ist ein Commit weiter hinten.

Sicherheit

Keine Cluster-Credentials in der CI, keine Laptops mit prod-Kubeconfig. Der Cluster holt sich, was er braucht.

Disaster Recovery

Cluster weg? Neuen Cluster anlegen, Argo CD installieren, auf Git zeigen – fertig.

Anti-Pattern: „GitOps“ mit Pipeline, die kubectl apply machtViele Teams nennen es GitOps, wenn Git der Auslöser einer Pipeline ist, die dann kubectl apply ausführt. Das ist Push-CI/CD – ohne Drift-Erkennung, ohne Self-Heal, mit Cluster-Credentials im CI-System. Der Unterschied ist kein Detail: Nur das Pull-Modell bemerkt Mareikes nächtliches scale.
Drift von Hand erkennen L4 Analysieren
  1. Vergleichen Sie den Istzustand mit Git: kubectl -n shop-manual get deploy kaffee-shop -o yaml gegen apps/shop/base/deployment.yaml.
  2. Notieren Sie drei Felder, die im Cluster stehen, aber nicht in Git (Tipp: status, metadata.managedFields, Defaults).
  3. Diskutieren Sie: Sind das alles „Drift“? Was müsste ein Tool ignorieren, was nicht?
Lösungshinweis
Typische Nicht-Drift-Felder: status, metadata.uid/resourceVersion/creationTimestamp, managedFields, vom API-Server ergänzte Defaults wie strategy.rollingUpdate.maxSurge. Echter Drift: spec.replicas: 0. Argo CD normalisiert genau diese Unterschiede vor dem Diff (Modul 5 und 10: ignoreDifferences).

Räumen Sie den manuellen Namespace wieder weg – ab jetzt macht das Argo CD: kubectl delete ns shop-manual

CRDCustom Resource Definition – erweitert die Kubernetes-API um eigene Objekttypen. Deshalb können Sie Argo CD selbst per GitOps verwalten – und deshalb ist Redis egal.

  2. kubectl -n argocd get crd | Select-String argoproj – welche drei CRDs sehen Sie?

Lösungshinweis
Der Application Controller ist ein StatefulSet, weil er beim Sharding (mehrere Replicas für viele Cluster) eine stabile Identität (Ordinal 0, 1, …) braucht, um Cluster deterministisch auf Shards zu verteilen. CRDs: applications, appprojects, applicationsets (jeweils .argoproj.io).

Windows-Stolperstein: PowerShell und DateikodierungWindows PowerShell 5.1 liest .ps1-Dateien ohne BOM als ANSI. Ein Umlaut oder ein Halbgeviertstrich wird dann zu ä-Salat und kann die Anführungszeichen-Erkennung zerlegen („Die Zeichenfolge hat kein Abschlusszeichen“). Halten Sie eigene Skripte ASCII-only oder speichern Sie sie in VS Code als UTF-8 with BOM. Derselbe Grund spricht für --patch-file statt Inline-JSON: kein Backslash-Escaping, das zwischen PowerShell 5.1 und 7 unterschiedlich ankommt.

Bewertung: Was ist an unserer Installation nicht produktionsreif?

Anti-Pattern-Sammlung (bewusst in dieser Schulung)
  • server.insecure=true + NodePort ohne TLS → Passwörter im Klartext im Netz. Produktion: Ingress mit TLS oder Argo CDs eigenes TLS.
  • Lokaler admin-Account aktiv → Produktion: SSO einrichten, admin.enabled: "false" in argocd-cm setzen.
  • Initial-Secret argocd-initial-admin-secret nie gelöscht → nach Passwortänderung löschen.
  • 1 Replica pro Komponente, kein HA → Redis-Ausfall stoppt UI.
  • Argo CD ist Cluster-Admin ohne Projekt-Grenzen (bis Modul 8).

Spielen Sie es durch: Erst ohne Haken „kubectl scale“ – Argo CD meldet OutOfSync, tut aber nichts. Mit Auto-Sync: Ein Commit wird sofort ausgerollt, aber der manuelle Eingriff bleibt! Erst mit Self-Heal wird der Eingriff zurückgedreht. „Service löschen“ zeigt, wofür Prune da ist.

Automated SyncsyncPolicy.automated: Argo CD synchronisiert, sobald sich Git ändert (neue Revision erkannt) – nicht bei Cluster-Änderungen.Beseitigt den Klick, nicht den Drift. Mareikes Eingriff überlebt Auto-Sync, bis der nächste Commit kommt.
Self-Healautomated.selfHeal: true: Argo CD synchronisiert auch dann, wenn sich der Cluster vom Git-Stand entfernt. Standard-Verzögerung 5 s, Backoff bei wiederholtem Drift.Das ist die Einstellung, die Mareikes Vorfall verhindert. Sie erzwingt gleichzeitig Disziplin: Manuelle Hotfixes im Cluster sind ab jetzt sinnlos – alles muss durch Git.
Pruneautomated.prune: true bzw. Haken im Sync-Dialog: Ressourcen löschen, die nicht mehr in Git stehen.Ohne Prune sammeln sich Leichen an (alte Services, umbenannte Deployments). Mit Prune löscht ein falscher Commit echte Dinge – deshalb PruneLast und Schutz-Annotationen kennen.

Auto-Sync für shop-dev einschalten – drei Wege

Reconcile-Timing beeinflussen

Standard: alle 180 s pollt Argo CD Git (timeout.reconciliation in argocd-cm). Schneller wird es mit einem Webhook: GitHub → Repo → Settings → Webhooks → Payload URL https://<argocd>/api/webhook, Content type application/json, Secret in argocd-secret unter webhook.github.secret. Lokal ohne öffentliche URL nicht demonstrierbar – im Kurs zeigen wir den Effekt mit argocd app get --refresh.

Anti-Pattern: Self-Heal an, aber HPA oder Operator ändern FelderEin HorizontalPodAutoscaler setzt spec.replicas. Self-Heal setzt es zurück auf den Git-Wert. HPA setzt es wieder hoch. Endlosschleife, Flapping, Alarme. Lösung: ignoreDifferences für /spec/replicas plus RespectIgnoreDifferences=true – oder Replicas gar nicht in Git pflegen (Modul 11).
Den Vorfall unmöglich machen L3 L5 Bewerten
  1. Aktivieren Sie Auto-Sync ohne Self-Heal (per Git-Commit auf argocd/apps/shop-dev.yaml und kubectl apply – oder UI). Führen Sie kubectl -n shop-dev scale deploy kaffee-shop --replicas=0 aus. Was passiert in 3 Minuten? Was nicht?
  2. Aktivieren Sie Self-Heal. Wiederholen Sie den Scale-Befehl. Beobachten Sie kubectl -n shop-dev get deploy -w.
  3. Löschen Sie service.yaml aus der Base-Kustomization (Datei behalten, nur Eintrag entfernen), pushen Sie. Mit Prune / ohne Prune – was zeigt die UI jeweils? Machen Sie den Commit danach rückgängig (git revert).
  4. Bewerten: Soll prod Auto-Sync + Self-Heal bekommen? Nennen Sie je ein Argument dafür und dagegen. (Wir entscheiden das in Modul 8 für Nordlicht Kaffee.)
Lösungshinweis
1: Nichts – Git hat sich nicht geändert. Die UI zeigt OutOfSync. 2: Innerhalb weniger Sekunden wieder 1 Replica. 3: Ohne Prune bleibt der Service, App zeigt „OutOfSync – 1 resource requires pruning“; mit Prune verschwindet er (Shop nicht mehr unter :8081 erreichbar). 4: Dafür: Drift-Schutz, Audit, schnelle Auslieferung. Dagegen: Ein fehlerhafter Merge geht ungebremst in prod; Freigabe-Prozesse (4-Augen) brauchen einen expliziten Sync-Schritt – üblich: Auto-Sync auf prod, aber mit Branch-Protection + Required Reviews im Git, oder Manual Sync + Notification.

Architektur-Diskussion: Ein Argo CD oder viele?

Hub-and-Spoke

Ein zentrales Argo CD verwaltet alle Cluster. Pro: eine UI, ein RBAC, Cluster-Generator. Contra: Single Point of Failure, Hub braucht Admin-Zugang überall, Netzwerkpfade.

Standalone pro Cluster

Jeder Cluster hat sein Argo CD (per Bootstrap-Skript). Pro: Isolation, kein Cross-Cluster-Zugang, Cluster stirbt allein. Contra: N UIs, Konfiguration vervielfacht (aber: aus Git!).

Phasen und Waves

Sync-PhasenEin Sync läuft in festen Phasen: PreSync → Sync → PostSync; bei Fehler zusätzlich SyncFail; beim Löschen der App PostDelete. Normale Ressourcen leben in der Sync-Phase.Migration = PreSync, Smoketest = PostSync, Alarm = SyncFail. Genau Nordlichts Anforderung.
Sync-WaveAnnotation argocd.argoproj.io/sync-wave: "N" (Default 0, negative erlaubt). Innerhalb einer Phase werden Ressourcen Wave für Wave angewendet; die nächste Wave startet erst, wenn alle Ressourcen der vorherigen Healthy sind. Ohne Waves gilt die eingebaute Kind-Reihenfolge (Namespace → CRD → … → Deployment).ConfigMap mit Feature-Flags in Wave -1, Datenbank in Wave 0, Shop in Wave 1: Der Shop startet erst, wenn die DB Healthy meldet.
HookRessource (meist Job, auch Pod oder Argo Workflow) mit Annotation argocd.argoproj.io/hook: PreSync|Sync|PostSync|SyncFail|PostDelete|Skip. Wird in der Phase ausgeführt, Sync wartet auf Abschluss. hook-delete-policy steuert Aufräumen: HookSucceeded, HookFailed, BeforeHookCreation (Default).Ein PreSync-Job, der fehlschlägt, stoppt den ganzen Sync – die Migration schützt das Deployment.

             [math]::Round(((Get-Date) - [datetime]$a.status.operationState.finishedAt).TotalMinutes) } else { '?' }
  [pscustomobject]@{ App=$a.metadata.name; Project=$a.spec.project; Sync=$sync; Health=$health; MinutenSeitLetztemSync=$since;

}
